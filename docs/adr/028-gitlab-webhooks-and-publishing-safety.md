# ADR-028: GitLab webhook intake and safe publishing

**Status:** Accepted · 2026-11-23

## Decision

**Webhook intake** (`POST /api/webhooks/gitlab/:repositoryId`):

- One secret per repository, generated by `connect-gitlab`. Only its SHA-256 is stored, and it is compared in
  constant time. Unknown repositories, malformed ids and bad tokens all return the same 401.
- The payload's `project.id` must equal the repository's GitLab project id. A token for project A therefore
  cannot trigger reviews of project B.
- Only MR `open`, `reopen` and `update` with `oldrev` (new commits) enqueue a review.
- `X-Gitlab-Event-UUID` is recorded in `webhook_deliveries` (unique), so replays answer `duplicate`. When the
  header is missing, a hash of repository, head SHA and action is used instead.
- The job carries identifiers only (no titles or descriptions). The worker re-fetches everything at the head SHA.
- JSON body limit is 2 MB. Rate limiting arrives in Phase 8.

**Publishing:**

- GitLab executes **quick actions** (`/merge`, `/approve`, `/assign`, …) found at the start of comment lines,
  as the bot user. Model output is influenced by the code under review, so a malicious MR could otherwise get
  itself merged. Every line outside code fences that starts with `/` is prefixed with a zero-width joiner.
- `@mentions` are defused, and Markdown and HTML are escaped.
- Duplicate-suppression markers are trusted only on notes authored by the bot account (`GET /user`). A marker
  typed by anyone else is ignored, so it cannot suppress a finding.
- Inline positions come from the diff (`planPublication`), never from model output. A rejected position falls
  back to the summary.
- The MR head is re-checked after the review. Results for a superseded commit are not published.

## Consequences

Covered by unit tests (sanitising, markers, planning) and by end-to-end integration tests: worker, PostgreSQL,
Redis and the fake GitLab.
